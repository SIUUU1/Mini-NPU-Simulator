# Mini NPU Simulator

AI(NPU)가 이미지를 판별할 때 사용하는 **MAC(Multiply-Accumulate) 연산**을 표준 라이브러리만으로
직접 구현한 콘솔 애플리케이션입니다. 입력 패턴을 두 개의 필터(Cross / X)와 위치별로 곱하고 더해
어떤 모양에 더 가까운지 판정합니다.

- 개발 환경: Python 3.8 이상 (검증 환경 3.12)
- 외부 라이브러리 사용 안 함 (NumPy·pandas 금지). 표준 라이브러리 `json`, `time`, `os` 만 사용
- 제출물: `main.py`, `data.json`, `README.md`

---

## 1. 실행 방법

```bash
python main.py
```

실행하면 모드를 선택합니다.

```
=== Mini NPU Simulator ===
[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

- **모드 1 (사용자 입력, 3×3)**: 필터 A → 필터 B → 패턴을 각각 3줄씩(공백 구분)으로 입력합니다.
  두 필터의 MAC 점수, 평균 연산 시간(ms), 판정(A / B / 판정 불가)을 출력합니다.
- **모드 2 (data.json 분석)**: 같은 폴더의 `data.json` 을 로드해 5×5·13×13·25×25 필터와
  패턴을 일괄 판정하고, 성능 표와 결과 요약을 출력합니다.

> `data.json` 은 반드시 `main.py` 와 **같은 폴더**에 있어야 합니다. 없으면 안내 문구를 출력하고
> 프로그램이 정상 종료합니다.

### 입력 예시 (모드 1)

```
선택: 1
필터 A → 0 1 0 / 1 1 1 / 0 1 0   (십자가 필터)
필터 B → 1 0 1 / 0 1 0 / 1 0 1   (X 필터)
패턴   → 1 0 1 / 0 1 0 / 1 0 1   (X 패턴)
=> A 점수: 1.0,  B 점수: 5.0,  판정: B
```

### data.json 스키마

```
{
  "meta":    { ... }, 
  "filters": { "size_5": {"cross": [[...]], "x": [[...]]}, "size_13": {...}, "size_25": {...} },
  "patterns":{ "size_5_1": {"input": [[...]], "expected": "x"}, ... }
}
```

`filters` 의 내부 키(`cross`/`x`)와 `patterns` 의 `expected`(`+`/`x`)는 서로 표기가 다르지만,
프로그램이 내부에서 표준 라벨(`Cross`/`X`)로 정규화해 비교합니다.

## 2. 구현 요약

### 2.1 데이터 구조
패턴·필터는 `list[list[float]]` 형태의 2차원 배열로 저장합니다. `pattern[i][j]` 로 특정 위치 값을
읽고 쓸 수 있으며, 3×3·5×5·13×13·25×25 등 임의의 n×n 크기를 처리합니다.

### 2.2 MAC 연산 (반복문 직접 구현)
`mac(pattern, filt)` 는 두 배열을 같은 위치끼리 곱해(Multiply) 모두 더한(Accumulate) 값을
반환합니다. 벡터화 라이브러리 없이 이중 `for` 문으로 구현했고, 결과는 float 을 반환할 수 있습니다.
보너스로 2차원 배열을 길이 N² 의 1차원 배열로 펼친 `mac_1d` 도 함께 제공해 접근 패턴을
단순화한 버전과 성능을 비교합니다.

### 2.3 라벨 정규화(표준화)
프로그램 내부는 표준 라벨 **`Cross`, `X`** 두 가지만 사용합니다. `normalize_label()` 이
아래 입력을 표준 라벨로 변환하며, 대소문자와 공백을 무시합니다.

| 원본 (expected) | 원본 (filter 키) | 표준 라벨 |
| --- | --- | --- |
| `+` | `cross` | `Cross` |
| `x` | `x` | `X` |

콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨을 기준으로 수행합니다. 데이터 파일이 서로 다른
표기를 쓰더라도 내부에서 하나로 통일하기 때문에, "표기 차이" 때문에 발생하는 오판정을 막을 수
있습니다.

### 2.4 스키마 검증 (모드 2)
패턴 키 `size_{N}_{idx}` 에서 N 을 추출하고, 해당 `size_N` 필터를 선택합니다. 이후
`input` 존재 여부, n×n 정방 여부, 필터 존재·크기 일치를 검사합니다. 문제가 있는 케이스는
조기 반환으로 방어하여 **프로그램을 중단시키지 않고** 해당 케이스만 FAIL 처리하고 사유를
메시지로 남깁니다. (최상위 `meta` 처럼 규격에 없는 키는 무시합니다.)

### 2.5 판정 및 동점 처리 (epsilon)
점수 비교는 부동소수점 오차를 감안해 **허용오차(epsilon) 기반**으로 수행합니다.
`abs(score_cross - score_x) < 1e-9` 이면 동점으로 보고, 모드 1 은 "판정 불가", 모드 2 는
`UNDECIDED` 로 판정합니다. 그 외에는 점수가 큰 쪽을 정답으로 봅니다.

## 3. 결과 리포트

모드 2(`data.json`) 실행 결과 요약은 다음과 같습니다.

```
총 테스트: 6개
통과: 3개
실패: 3개
실패 케이스:
  - size_5_1:  동점(UNDECIDED) 처리 규칙에 따라 FAIL
  - size_13_2: 동점(UNDECIDED) 처리 규칙에 따라 FAIL
  - size_25_1: 동점(UNDECIDED) 처리 규칙에 따라 FAIL
```

케이스별 점수:

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
| --- | --- | --- | --- | --- | --- |
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

성능 분석 표 (평균/2000회, 측정값은 실행 환경에 따라 달라짐):

| 크기 | 2D 시간(ms) | 1D 시간(ms) | 연산 횟수(N²) |
| --- | --- | --- | --- |
| 3×3 | 0.0006 | 0.0008 | 9 |
| 5×5 | 0.0013 | 0.0009 | 25 |
| 13×13 | 0.0069 | 0.0053 | 169 |
| 25×25 | 0.0232 | 0.0227 | 625 |

### 3.1 실패 원인 분석 — "데이터 vs 로직 vs 수치 비교"로 분리 진단
세 실패 케이스(`size_5_1`, `size_13_2`, `size_25_1`)는 모두 **수치 비교(부동소수점) 문제**로,
데이터가 의도적으로 심어 놓은 함정입니다. 세 경우 모두 Cross 점수와 X 점수의 **참값(수학적
값)이 정확히 같습니다.**

- `size_5_1`: Cross 는 `0.9` 한 항, X 는 `0.1` 을 아홉 번 더합니다. 둘 다 참값은 0.9 지만
  `0.1×9 = 0.8999999999999999` 이 되어 X 가 미세하게 작아집니다.
- `size_13_2`: Cross 는 `0.3` 을 스물다섯 번, X 는 `7.5` 한 항입니다. 둘 다 참값은 7.5 지만
  `0.3×25 = 7.499999999999997` 이 되어 Cross 가 미세하게 작아집니다.
- `size_25_1`: Cross 는 `4.9` 한 항, X 는 `0.1` 을 마흔아홉 번 더합니다. 둘 다 참값은 4.9 지만
  `0.1×49 = 4.899999999999999` 이 되어 X 가 미세하게 작아집니다.

세 경우의 실제 점수 차이는 약 `1e-15 ~ 1e-16` 수준으로, 이는 IEEE754 부동소수점의 표현 한계
때문에 생기는 **오차(노이즈)이지 의미 있는 차이가 아닙니다.** 따라서 허용오차 정책(`< 1e-9`)이
이를 동점으로 흡수해 `UNDECIDED` 로 판정하고, `expected` 가 정해진 라벨(X/Cross)이므로
규칙상 FAIL 이 됩니다. 이 실패는 로직 버그가 아니라 **데이터 자체가 두 필터에 똑같이 반응하도록
설계된, 판별 불가능한 경계 사례**입니다.

- **라벨/스키마 문제였다면:** `expected`(`+`/`x`)·필터 키(`cross`/`x`)의 표기 차이는
  `normalize_label()` 이 표준 라벨로 통일하므로 오판정으로 이어지지 않습니다. 크기 불일치나
  키 형식 오류는 케이스 단위 FAIL 로 격리됩니다. 이번 데이터에는 이 유형의 실패가 없습니다.
- **로직 문제였다면:** MAC 합산이나 대소 비교가 틀렸다면 점수 차이가 큰 정상 케이스들도
  광범위하게 FAIL 했을 것입니다. 정상 3개(size_5_2, size_13_1, size_25_2)가 모두 PASS 라는
  사실이 MAC·판정 로직이 올바름을 방증합니다.

### 3.2 왜 epsilon 정책이 필요한가
만약 허용오차 없이 `>` 로만 단순 비교했다면, 같은 세 케이스에서 아래처럼 **확신에 찬 오답**이
나옵니다.

| 케이스 | epsilon 미적용 판정 | epsilon 적용 판정 | expected |
| --- | --- | --- | --- |
| size_5_1 | Cross (오답) | UNDECIDED | X |
| size_13_2 | X (오답) | UNDECIDED | Cross |
| size_25_1 | Cross (오답) | UNDECIDED | X |

즉 부동소수점 노이즈의 방향에 따라 판정이 뒤집혀 **틀린 라벨을 확신 있게 출력**하게 됩니다.
epsilon 정책은 이 노이즈를 "동점"으로 인식해, 확신에 찬 오답 대신 "판정 불가(UNDECIDED)" 라는
정직한 결과를 내도록 만듭니다. 이것이 부동소수점 비교에 허용오차가 반드시 필요한 이유입니다.

### 3.3 시간 복잡도 분석 — O(N²)
n×n 패턴과 필터의 MAC 은 모든 위치를 한 번씩 곱하고 더하므로 곱셈 횟수가 정확히 **N²** 입니다.
표의 "연산 횟수" 열이 곧 N² 이며(9 → 25 → 169 → 625), 측정 시간도 대체로 이 값에 비례해
증가합니다. 3×3처럼 매우 작은 크기는 함수 호출·반복 오버헤드가 상대적으로 커서 정확한 비례가
드러나지 않지만, 13×13 → 25×25 구간에서는 연산량이 약 3.7배(169→625) 늘 때 시간도 약 3배
이상 증가하는 것을 확인할 수 있습니다. 실제 AI는 수백×수백 필터를 수천 개 사용하므로, N 이
커질수록 N² 로 폭증하는 이 연산을 병렬 처리하기 위해 NPU 가 필요하다는 결론으로 이어집니다.

### 3.4 1차원 최적화
2차원 접근(`mac`)은 매 반복마다 행 리스트를 인덱싱하지만, 1차원(`mac_1d`)은 길이 N² 배열을
순차 접근합니다. 표의 2D/1D 열이 동일 입력·동일 반복 횟수에서의 비교 결과이며, 소·중형
크기에서 1D 가 대체로 근소하게 빠릅니다. 다만 파이썬 인터프리터 오버헤드가 지배적인 구간에서는
차이가 작고 실행마다 변동이 있을 수 있습니다. (패턴 생성기 `make_cross`/`make_x` 는 보너스 2로
구현되어 성능 표의 입력 생성에 재활용됩니다.)

## 4. 재현성

- **모드 1:** 위 입력 예시(십자가 필터 A, X 필터 B, X 패턴)를 넣으면 항상
  `A 점수: 1.0`, `B 점수: 5.0`, `판정: B` 가 출력됩니다. 필터 A·B를 같게 넣으면
  `판정: 판정 불가 (|A-B| < 1e-09)` 가 출력됩니다.
- **모드 2:** 제공된 `data.json` 분석 시 6개 케이스 중 **3 PASS / 3 FAIL**
  (`size_5_1`, `size_13_2`, `size_25_1`)이 항상 동일하게 나오며, 총/통과/실패 합계가
  일치합니다.
- **의도적 오류 입력:** 모드 1에서 행·열 개수가 맞지 않거나 숫자가 아닌 값을 넣으면 안내 문구를
  출력하고 재입력을 유도합니다. 모드 2에서 크기 불일치·알 수 없는 라벨·잘못된 키가 있어도
  프로그램이 중단되지 않고 해당 케이스만 FAIL 로 처리합니다.
